# Продуктовая аналитика площадки объявлений о недвижимости

Учебный кейс: анализ продукта, похожего на сервис объявлений о продаже и аренде жилья в Казахстане. Работа с обеими сторонами маркетплейса — пользователями, которые ищут жилье, и объявлениями.

Реальных данных у меня нет, поэтому сначала написал генератор, который воспроизводит то, с чем приходится иметь дело в реальной аналитике: недельную сезонность, тяжелый хвост активности (агенты), самоотбор при покупке платных услуг. Плюс синтетики в том, что истинные эффекты известны заранее, и можно проверить, находят ли их методы.

## Что внутри

| | Вопрос | Методы |
|---|---|---|
| [01_product_metrics](notebooks/01_product_metrics.ipynb) | В каком состоянии продукт? Где точки роста? | DAU/WAU/MAU, воронка по платформам, когортный retention, ликвидность объявлений |
| [02_ab_test_listing_card](notebooks/02_ab_test_listing_card.ipynb) | Раскатывать ли новую карточку объявления? | SRM, A/A на предпериоде, дельта-метод для ratio-метрик, линеаризация, CUPED, бутстрап, поправка Холма для сегментов |
| [03_promotion_effect](notebooks/03_promotion_effect.ipynb) | Сколько реально дает платное продвижение объявления? | модель склонности (logit), matching, difference-in-differences, event study, плацебо-тест |

Еще:
- [`src/abtest.py`](src/abtest.py) — функции для анализа тестов, покрыты тестами в [`tests/`](tests/) (в т.ч. проверка, что дельта-метод держит FPR на А/А);
- [`sql/`](sql/) — запросы в диалекте BigQuery: сборка витрин из сырых событий, воронка, retention, расчет эксперимента с дельта-методом прямо в SQL;
- [`dags/`](dags/) — DAG для Airflow: ежедневная сборка витрин, проверки качества данных, ежедневная проверка SRM по активным экспериментам.

## Основные результаты

**Состояние продукта.** Конверсия просмотр → контакт ~6.5%, на вебе ниже (5.9%) и меньше просмотров на пользователя. 10% самых активных пользователей дают 44% просмотров. Объявления дороже медианы района на 15%+ и объявления без фото заметно хуже получают контакты.

**A/B тест новой карточки.** CR просмотр → контакт **+2.8%** (CUPED, p ≈ 0.01), guardrail-метрики не просели. Эффект держится на мобильных приложениях, на вебе около нуля. Решение — раскатка на приложения, по вебу отдельная доработка.

<img src="reports/figures/02_aa_pvalues.png" width="800">

*Почему CR нельзя считать z-тестом по просмотрам: на 1000 А/А тестах наивный подход дает 25% ложных прокрасов вместо 5%.*

**Платное продвижение.** Наивное сравнение "до/после" дает +60% к просмотрам, но продвижение покупают сразу после просадки — часть роста просто возврат к норме. Matching + DiD: **+46% просмотров и +30% контактов** (истинные значения, заложенные в генератор, — +45% и +30%).

## Как запустить

```bash
pip install -r requirements.txt
python src/generate_data.py --out data      # несколько секунд, ~1.2 млн строк
pytest tests
jupyter lab notebooks/
```

## Структура данных

| таблица | гранулярность | поля |
|---|---|---|
| `users` | пользователь | платформа, город, роль (buyer / renter / seller / agent), дата регистрации |
| `user_daily` | пользователь × день | сессии, поиски, просмотры объявлений, избранное, контакты |
| `exp_exposures` | пользователь | эксперимент, вариант, дата первой экспозиции |
| `listings` | объявление | город, район, тип сделки, тип продавца, комнаты, площадь, цена, кол-во фото |
| `listing_daily` | объявление × день | просмотры, контакты, флаг продвижения |
| `promotions` | покупка | объявление, дата начала, пакет |

Контакт = показ телефона или первое сообщение в чат по объявлению.

## Что можно добавить

- Uplift-модель (кому предлагать продвижение) и проверить ее через A/B тест рекомендации.
- Эксперимент на стороне продавцов: подсказка рыночной цены при подаче объявления.
- Sequential testing, чтобы безопасно смотреть на результаты теста до его окончания.
